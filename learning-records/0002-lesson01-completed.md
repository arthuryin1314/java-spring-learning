# Lesson 0001 完成:程序结构与编译模型

两个练习都完成,过程中暴露了一个真实错误,修复方式和思考习惯都值得记录。

## 练习 1

`Roster.java` 编写并运行成功,输出三行完全符合要求。过程中踩到一个坑并自己定位:

- **错误**:把 `println` 的参数写成单引号 `'Course Roster'`,触发编译错误 `Too many characters in character literal`。
- **根因**:Java 单引号 `'...'` 是 `char` 字面量,必须**恰好一个字符**;双引号 `"..."` 才是 `String`。这和 Python/TS 里单双引号完全等价的习惯冲突,是从这两门语言迁移过来的人最容易踩的第一个坑。
- **修复过程**:我先解释了报错含义(char vs String 的字面量语法),给方向提示(IDEA 自带的 quick-fix 提示"Convert to string literal"是线索),用户自己改的,没有直接给代码。

## 练习 2(设计题:非 public 类是否也要求文件名匹配)

- 用户第一次回答时**凭直觉猜测**"不这样就编译错误",没有实际验证。
- 被要求"用实验代替猜测"后,自己新建了一个不带 `public` 的 `UserService` 类放在任意文件名下测试,**确认编译通过**——验证了"只有 public 类才强制文件名匹配"这一规则。
- 用户主动承认第一次是猜的,并认可"验证代替猜测"这个方法。

## Implications

- 用户能够根据报错信息里的线索(如 IDE 的 quick-fix 建议)自主定位并修复问题,不需要给出具体代码就能收敛到正确答案——第一课的报错处理流程(先解释含义,再给方向)是有效的,继续保持。
- 用户有"先猜后验证"的倾向,需要适度提醒用"跑一下看看"代替"猜答案",尤其是遇到 Java 规则和 Python/TS 直觉冲突的地方。
- 字符串 vs 字符字面量的区别已经通过实战踩坑掌握,不需要再单独复习,但后续讲到 `char` 类型本身时可以简单提一句呼应这次的报错。
- 编译模型、public class 文件名规则、main 签名均已通过练习验证,Lesson 1 目标达成,可以进入下一课。
